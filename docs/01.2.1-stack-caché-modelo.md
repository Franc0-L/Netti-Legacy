## 1.3 Caché y publicación

**La diferencia que importa**:

| API                                 | Comportamiento                                      | Dónde                   |
| ----------------------------------- | --------------------------------------------------- | ----------------------- |
| `revalidateTag(tag, { expire: 0 })` | Expira ya; la próxima request es un miss bloqueante | Route Handlers, cron    |
| `updateTag(tag)`                    | Expira ya y garantiza lectura de lo escrito         | **Solo Server Actions** |

Las mutaciones del panel son Server Actions, así que usan `updateTag`. El autor ve su cambio publicado al volver al sitio, sin esperar la segunda visita.

**Caché: lo que no está garantizado.** `"use cache"` es almacenamiento en memoria. En entornos serverless no es seguro que persista entre invocaciones ni que se comparta entre instancias; `cacheLife("max")` no convierte la caché local en almacenamiento remoto compartido. Para una caché distribuida real se necesita `use cache: remote` con un handler, que tiene coste y latencia asociados.

Por tanto, la frase de `00-vision.md` —"la lectura pública no despierta la base"— no está demostrada solo por usar Cache Components. Se debe:

1. Prerenderizar las páginas públicas que se conozcan durante el build cuando sea viable.
2. Separar el shell estático de las consultas realmente dinámicas.
3. Probar explícitamente `use cache` en el despliegue real (Fase 0).
4. Si el contenido depende de caché compartida en runtime, evaluar `use cache: remote`, estudiando su costo y latencia.
5. Mantener una alternativa de lectura estática que no dependa de una conexión a Neon para las páginas ya generadas.

Este punto es un bloqueante de la Fase 0: sin esta prueba, no apruebo la arquitectura de producción.

**Invalidación granular**: una función pura `affectedTags(before, after)` devuelve los tags de la entrada, del listado del `kind`, de las etiquetas **viejas y nuevas**, y `home` solo si cambió un campo que se renderiza en la portada (`status`, `published_at`, `featured`, `title`, `description` o `score`). Corregir una tilde en el cuerpo no invalida la portada.

**Inventario de proyecciones.** Un tag por entrada no alcanza si el contenido aparece en varios lugares. La tabla es chica y explícita:

| Proyección            | Tags                                               |
| --------------------- | -------------------------------------------------- |
| Detalle               | `article:<kind>:<slug>`, `kind:<kind>`, `articles` |
| Listado por colección | `kind:<kind>`, `articles`                          |
| Portada               | `home`                                             |
| Etiquetas             | `tag:<tag>` (viejas y nuevas)                      |
| Cambio de etiquetas   | `tags` (invalida el índice de etiquetas visibles)  |
| Ficha de juego        | `game:<id>`, `kind:game`                           |
| Sitemap y RSS         | `articles`, `kind:<kind>`                          |
| Redirecciones         | `redirects`                                        |

`affectedTags` agrega `redirects` cuando cambia el slug, y `game:<id>` cuando una reseña asociada a una ficha cambia de forma que afecte su listado de reseñas. `affectedTags` es la implementación, no la documentación: la tabla es la fuente. Los tests de integración publican, cambian slug, borran y restauran, y comprueban las siete proyecciones.

**Programados**: `published_at` futuro no se ve porque el predicado público exige `published_at <= now()`. Un job cada 30 minutos llama a un Route Handler protegido que revalida lo que cruzó la hora. Si falla, el artículo aparece en la siguiente revalidación: retraso, no fuga.

**Quién corre ese job**: GitHub Actions es el valor por defecto. Los Cron Jobs de Vercel en Hobby corren como máximo **una vez por día**, y los Schedules —que sí permiten cada 15 minutos— siguen en beta y tienen 5.000 ejecuciones por período. GitHub Actions es gratis, estable y no depende de un producto beta. El endpoint usa `revalidateTag(tag, { expire: 0 })` para forzar un miss bloqueante en la próxima lectura. Si Schedules sale de beta, se migra sin tocar código.

**Cardinalidad de tags**: solo entidades y grupos (`articles`, `kind:review`, `article:review:slug`, `tag:analisis`). Nunca un tag derivado de entrada del usuario (`search:<consulta>`, `article:<id-de-visita>`): crecerían sin límite y el usuario público controlaría qué se invalida.

## 1.4 Datos y modelo

Ver `02.1-modelo-tablas.md`. Resumen:

- `games` + `articles(kind)` + `media` + `media_variants` + `article_revisions` + `sessions` + `login_attempts` + `redirects`.
- Sin `users`, sin `article_bodies`, sin estado `scheduled`.

### 2.2 Lectura pública

1. La ruta pide `getArticle(kind, slug)`.
2. Si hay entrada en caché, se sirve.
3. Si no, Drizzle consulta Neon y el resultado queda cacheado con `cacheLife('max')`.
4. Markdown → HTML sanitizado.
5. SEO, canonical, JSON-LD.

**Medición de caché.** `x-vercel-cache` evidencia caché de respuesta de ruta/CDN, no necesariamente que la lectura de datos no haya consultado Neon. Para validar que la lectura pública no despierta la base se mide por separado:

- Generación estática / ISR: `x-vercel-cache` y ausencia de CU-h en Neon.
- Lectura de datos con `use cache` runtime: CU-h de Neon antes y después de visitas repetidas.

**Contrato de `getArticle`**:

```ts
// Índice de slugs visibles de artículos por kind. Se usa para evitar despertar la base
// con slugs aleatorios y para no aplicar cacheTag a entrada de usuario.
// Se invalida cuando el cron toca `kind:<kind>` o `articles`.
export async function getVisibleArticleSlugs(
  kind: ArticleKind,
): Promise<string[]> {
  "use cache";

  cacheTag(`kind:${kind}`, "articles");
  cacheLife("max");

  const now = new Date();

  const rows = await db.query.articles.findMany({
    columns: { slug: true },
    where: and(
      eq(articles.kind, kind),
      eq(articles.status, "published"),
      lte(articles.publishedAt, now),
    ),
  });
  return rows.map((r) => r.slug);
}

// Índice de slugs visibles de juegos. Se usa para validar slugs de fichas sin tocar Neon.
export async function getVisibleGameSlugs(): Promise<string[]> {
  "use cache";

  cacheTag("kind:game", "games");
  cacheLife("max");

  const rows = await db.query.games.findMany({
    columns: { slug: true },
    where: eq(games.status, "published"),
  });
  return rows.map((r) => r.slug);
}

// Índice de etiquetas usadas por artículos publicados. Se usa para validar slugs de etiquetas.
export async function getVisibleTagSlugs(): Promise<string[]> {
  "use cache";

  cacheTag("tags", "articles");
  cacheLife("max");

  const now = new Date();

  const rows = await db.query.articles.findMany({
    columns: { tags: true },
    where: and(
      eq(articles.status, "published"),
      lte(articles.publishedAt, now),
    ),
  });
  // Expande el array de etiquetas de cada artículo y deduplica
  const tags = new Set<string>();
  for (const row of rows) {
    for (const tag of row.tags) {
      tags.add(tag);
    }
  }
  return Array.from(tags);
}

// ArticleKind importado de lib/tags.ts
export async function getArticle(
  kind: ArticleKind,
  slug: string,
): Promise<PublicArticle | null> {
  "use cache";

  cacheTag(`article:${kind}:${slug}`, `kind:${kind}`, "articles");
  cacheLife("max");

  const validSlugs = await getVisibleArticleSlugs(kind);
  if (!validSlugs.includes(slug)) return null;

  const now = new Date();

  return db.query.articles.findFirst({
    where: and(
      eq(articles.kind, kind),
      eq(articles.slug, slug),
      visibleArticle(now),
    ),
  });
}
```

**Importante:** `new Date()` dentro de `"use cache"` se evalúa **una sola vez**, al llenar la entrada de caché. No es "un reloj fresco por consulta": el valor de `now` queda congelado con la caché. Un artículo programado cuyo `published_at` cruza la hora seguirá devolviendo `null` hasta que el cron invalide la entrada con `revalidateTag(tag, { expire: 0 })`. No confiar en `now` dentro de `"use cache"` para decidir visibilidad en tiempo real; la invalidación programada es el mecanismo correcto.

Si el artículo no existe, `getArticle` retorna `null`. La consulta al índice de `redirects` es responsabilidad del **resolver de rutas** (capa de routing), no de `getArticle`: el resolver primero consulta `getVisibleArticleSlugs(kind)` y, si el slug no está, consulta `getRedirectIndex()` (cacheado bajo el tag `redirects`) para responder 308 si existe una redirección; si no, 404. Nunca en el proxy ni en cualquier URL arbitraria.

El resolver es común a todas las rutas de contenido. Una URL que cambia de colección (`/resenas/juego-x` → `/juegos/juego-x`) se redirige igual, porque el mapa se consulta después de que la ruta de contenido no encontró la fila, no después de que el artículo exista en la colección anterior.

### 2.3 Escritura

1. Server Action → `requireSession()` → verifica `Origin`.
2. El servidor completa `published_at` si hace falta (antes de validar con Zod).
3. Zod → `articleSchema`.
4. Dentro de **una transacción**: `UPDATE ... WHERE id AND version RETURNING version` + `INSERT` del snapshot en `article_revisions`.
5. Después del `COMMIT`: `updateTag` sobre los tags de `affectedTags()`.
6. Devuelve `{ ok, version }` o `{ ok: false, errors, current? }`.

Invalidar antes de confirmar publica un estado que todavía puede revertirse.

### 2.4 Límites intencionales

- Sin comentarios ni cuentas de lectores.
- Nada se escribe al disco local.
- Sin API pública.
- Sin duplicar lógica entre Server Actions y Route Handlers.

### 2.5 Contratos de `lib/`

Estos contratos están listados aquí para que la implementación no parta de cero:

**`lib/storage.ts`** — abstrae el proveedor de archivos (hoy Vercel Blob):

```ts
export interface StoredObject {
  key: string; // articles/<uuid>.webp, nunca slug ni nombre original
  url: string; // pública, derivada de la respuesta de Blob
  bytes: number;
}

export interface Storage {
  put(
    key: string,
    body: ReadableStream | Blob | ArrayBuffer,
    options: {
      contentType: string;
      cacheControlMaxAge: number;
    },
  ): Promise<StoredObject>;
  del(keys: string[]): Promise<void>;
  list(args: { prefix: string; cursor?: string; limit?: number }): Promise<{
    objects: Array<{ key: string; bytes: number; uploadedAt: Date }>;
    nextCursor: string | null;
  }>;
}
```

- `put` usa claves exactas (`addRandomSuffix: false`) para que el `key` sea estable y el `url` predecible.
- `del` es idempotente; si falla alguna variante, se registra en `storage_orphans` para reconciliación posterior.
- Credenciales: OIDC en Vercel (`VERCEL_OIDC_TOKEN` + `BLOB_STORE_ID`), `BLOB_READ_WRITE_TOKEN` en desarrollo local y CI.
